# RUDA Fashion B2B Platform

Multi-merchant fashion wholesale platform with buyer, merchant, and platform-administration portals.

See [docs/真实功能知识库总览.md](docs/真实功能知识库总览.md) for the repository-wide feature map, implementation boundaries, documentation index, and outstanding verification gaps. It distinguishes code presence from integration and production acceptance.

## Development

**Prerequisites:** Node.js and PostgreSQL.

1. Copy [.env.example](.env.example) to `.env` and provide development-only values.
2. Install dependencies: `npm install`
3. Generate the Prisma client: `npm run db:generate`
4. Apply migrations: `npm run db:migrate`
5. Seed demonstration data only in development: `npm run db:seed`
6. Run the application: `npm run dev`

## Production deployment

1. Provide all required production environment variables, including unique JWT secrets.
2. Run `npm run start:production`.

The production startup script applies migrations and builds the application. It deliberately does **not** seed data or create default accounts. Provision the first administrator and all production data through approved administrative procedures.

Before a production release, review the pending migrations and take a verified backup. `npm run start:production` requires `ALLOW_PRODUCTION_MIGRATIONS=true`; it builds, writes a protected custom-format backup under `release/pre-deploy-backups`, applies migrations, restarts PM2, and runs `npm run smoke:post-deploy`. The post-deploy smoke verifies health, database readiness, the primary-domain Italian redirect, localized title/language/canonical/hreflang for all 60 combinations of 12 locales and five public pages (home, catalog, showrooms, trends, and about), and public sitemap/agent discovery responses. Do not enable the migration flag until the release and maintenance window are approved. For a recovery rehearsal, create a separate empty PostgreSQL database named `ruda_recovery_drill_*`, set `RECOVERY_DATABASE_URL` and `RECOVERY_BACKUP_FILE` to a backup and its adjacent `.json` manifest, then run `npm run db:recovery:drill`; the restored drill database is intentionally retained for inspection.

The POS API E2E journey requires an isolated database whose name contains a delimited `test` or `e2e` marker, plus `E2E_MERCHANT_EMAIL` and a test-only password of at least 16 characters. Run `npm run test:e2e:seed` with `NODE_ENV=test` and that database in `DATABASE_URL`, start the test application against the same database, set `E2E_BASE_URL`, then run `npm run test:e2e`. Local databases are allowed by default; using a remote test database or target additionally requires `E2E_ALLOW_REMOTE_DATABASE=true` or `E2E_ALLOW_REMOTE_TARGET=true`. Never point the seed or E2E run at production.

### Database backups and cloud sync

Platform administrators with the `settings.database` permission can manage backups in the database operations center. Backups are created with PostgreSQL `pg_dump` in custom format, written to a private staging file, validated with `pg_restore --list`, and atomically published with a SHA-256 checksum. The daily schedule supports an administrator-selected IANA timezone and time; local retention is configurable from 1 to 365 dumps (default 30). Manual creation, download, integrity re-verification, per-backup cloud-sync retry, and provider connection tests are available there. Local backup deletion additionally requires `settings.database.backup_delete` (or super-admin access) and exact-filename confirmation; deleting a local file never deletes remote copies. Backup files are restricted to owner-only permissions, jobs are serialized, and the scheduler persists its last successful run date so restarts do not duplicate the daily backup.

The database center loads its overview, backup inventory, cloud-sync configuration, schedule, Google Cloud settings, and media-backup status independently. A failed request shows a section-specific error and retry without hiding the other sections or the Google Cloud credential form. Its recovery dashboard summarizes the most recent verified database backup, remote copies, media snapshot, and Cloud SQL recovery drill, alongside a recovery checklist. The displayed RPO (24 hours) and RTO (4 hours) are operational targets, not a guarantee; validate the RPO against the age of a successful backup and measure the RTO through regular isolated recovery drills before adopting stricter service objectives.

The mobile administrator console includes read-only finance settlement and audit-log views, a responsive database/recovery center, and the risk monitor. Sensitive platform settings remain in the full platform settings center; the mobile settings view provides a direct switch to that responsive interface rather than duplicating secret-entry forms.

### ModaGPT merchant design library

ModaGPT image-generation and AI Try-On results are stored only after the merchant explicitly chooses **Save to designs**. Saved design metadata is tenant-scoped in PostgreSQL; image files use the existing private S3-compatible media storage and are served through short-lived signed URLs. Apply the `MerchantModaGptDesign` migration before enabling the library. If media storage is not configured, saving and loading stored images return an explicit unavailable error; the app does not fall back to public URLs or database image blobs. The merchant can browse, favorite, download, or permanently delete saved designs from the ModaGPT workspace.

The platform-admin navigation is divided into two top-level areas: **运营主页** for marketplace operations, fulfillment, finance, growth, support, and content; and **平台设置** for integrations, notifications, AI configuration, database recovery, and audit. Platform configuration screens are grouped under **系统设置**, while database and audit functions are under **平台运维**. Both desktop and mobile menus use the shared `src/apps/platform-admin-common/components/admin/adminNavigation.ts` registry so labels and module ownership are maintained once. The operational-intelligence overview is a compact, live summary while the risk monitor is the persisted alert investigation workflow; media-backup destination credentials remain managed in integrations while the database center consumes backup status and recovery actions, so these related surfaces are complementary rather than duplicate controls.

Cloud sync is optional and can target a dedicated S3-compatible backup bucket, Google Drive, or both. Database-backup S3 credentials are separately encrypted and configured in the database center, apart from the media-storage credentials; older installations that already enabled backup sync continue to work with their shared credentials until migrated. Use a backup-only access key, enable bucket versioning/object lock where supported, and apply a provider lifecycle policy. The app never deletes remote backup objects; retries first compare the existing object size and SHA-256 metadata and refuse to overwrite a mismatched object. The S3 connection test writes and verifies one small, fixed health-check object which it reuses.

Image/video object storage is configured in the platform admin integrations page. A separate media-backup S3-compatible destination can be configured there using its endpoint, bucket, prefix, and backup-only credentials; the credentials are encrypted and are never returned. Enable the daily database backup schedule to have a media snapshot start automatically after each successful scheduled database backup, or start one on demand. Each run streams current source objects to a unique run prefix, checks copied object sizes, and writes a manifest. The admin can restore missing objects from a completed manifest; restore never overwrites an existing object and reports size conflicts. This is a current-object snapshot, not a copy of provider object-version history. Configure versioning/retention on the destination bucket. Database dumps include inline database media data but cannot include local-filesystem media; preserve legacy files stored only on local disk separately.

For Google Drive, enable the Drive API in Google Cloud, create a dedicated backup-only service account/key, share only the destination folder with its service-account email, then paste the JSON key and folder ID into the database center. The key is encrypted at rest and is never returned by the settings API. A blank key on save preserves the existing key. The Drive connection check validates credentials and folder access without creating or deleting user files.

The database center also has a separate Google Cloud project integration. Configure its project ID and a dedicated read-only service-account key; it uses the `cloud-platform.read-only` OAuth scope to inspect Cloud SQL instances, automated-backup/PITR settings, recent Cloud SQL backup runs, and Cloud Storage bucket versioning/retention settings. Enable the Cloud SQL Admin API and Cloud Storage API, and grant this account only Cloud SQL Viewer and Storage Viewer (or equivalent read-only permissions). This account is distinct from the Google Drive uploader. Resource discovery is on demand and reports Cloud SQL and Storage API permission failures separately.

For a Cloud SQL MySQL or PostgreSQL recovery drill, save a second, separate recovery-operator service-account key in the database center. Its JWT uses the `cloud-platform` scope and it needs Cloud SQL permissions to inspect source/backup metadata, create a Cloud SQL instance, restore a backup to that new instance, poll operations/list databases, and delete the temporary instance. Prefer a custom IAM role constrained to the project and those actions; never reuse the Drive uploader or application database credentials. Select a discovered MySQL/PostgreSQL instance and a `SUCCESSFUL` Cloud SQL backup run, acknowledge the per-run cloud cost, and confirm the exact action in the UI. The drill creates an unpredictable `ruda-drill-*` instance in the same project, matching the source tier/disk settings with public IPv4 disabled. It never uses or overwrites the source instance and never restores local PostgreSQL `.dump` files to Cloud SQL. The result is successful only after the restore operation completes, at least one non-system database is present, and the temporary instance has been deleted. Drill records are stored owner-only, audited, reconciled after service restarts, and offer an explicit cleanup retry if Google Cloud deletion fails. Cloud SQL restore documentation notes that restores overwrite existing targets; this implementation therefore creates a fresh target and refuses to delete it unless its ownership labels exactly match the persisted drill record.

Cloud uploads run independently from local backup creation: a remote-provider failure leaves the local backup available and is shown per provider, with a retry action. Remote copies are not deleted when old local files are pruned or when a local backup is deleted; configure retention/lifecycle rules in the destination provider. Database-backup S3 credentials need bucket access, `PutObject`, and `GetObject`/`HeadObject` access; they do not need `DeleteObject`. Media snapshot credentials need source `ListBucket`/`GetObject` and destination `PutObject`/`HeadObject` access. Cloud-provider configuration does not change the live PostgreSQL connection: production database endpoints and credentials remain deployment-managed. Configure Cloud SQL point-in-time recovery separately.

Google Cloud inventory and protection checks remain read-only; the separate recovery-drill account is used only after explicit, per-run confirmation to create/restore/delete a disposable target. This is a technical restore verification, not an application-level production recovery or failover: it does not change Cloud SQL backup/PITR configuration, switch the production database, run business-level data checks, or promise a recovery-time objective. Keep production recovery approval/runbooks, application smoke tests, and recurring drills in place.

### AI Employee Operations Center (first phase)

ModaGPT product direction, provider boundaries, implementation status, and acceptance criteria are consolidated in the [RUDA feature knowledge base](docs/真实功能知识库总览.md). Roadmap items are not considered shipped until implementation and acceptance checks are complete.

Platform administrators with the existing `settings.ai_support` permission can open **AI 大脑运营中心** to manage the persisted AI employee catalog, product version labels, descriptions, and lifecycle metadata. Publishing a definition as `available` makes it visible for merchant installation. The initial catalog definitions are inserted by the `add_ai_employee_registry` Prisma migration.

The merchant **AI 员工** page lists employee definitions and records per-merchant installations. Owners and merchant employees with `employees.manage` can request an employee; a platform administrator must approve the request after publishing the employee as `available`. Approval starts with an empty permission set, and the merchant can pause an approved employee. Installations are tenant-scoped. The currently executable roles are Product Manager, Inventory Manager, and Sales Manager; each tool requires a separate, narrowly scoped merchant permission. The Product Manager can search only the merchant's non-archived product catalog after receiving `product.catalog.read`; its natural-language request is converted into a fixed product-search tool call. The task endpoint returns at most 25 limited product records, and the standalone read-only tool endpoint returns at most 50. The AI Team command panel can delegate one allowlisted product, inventory, replenishment, or sales-summary task per request to an active, authorized employee; it rechecks permissions before reading data, writes employee audit events, and explicitly declines unsupported work. Inventory and sales capabilities and their limits are described below. No employee can create orders, contact buyers, change stock, perform marketing actions, fan out to multiple workers in one run, or run autonomous/background tasks. From a search result, the Product Manager can generate a title/description proposal based only on the current product record. Proposals are persisted as `pending` drafts without changing products; regenerating for the same product and language supersedes its previous pending draft. Owners and employees with `employees.manage` can review the persistent pending-draft queue without repeating the product search, edit the text, then explicitly apply or reject it. Applying updates only the chosen language's title and description, never price, stock, visibility, or publication state. If the source fields changed since generation, the apply request is rejected, the draft is marked `stale`, and the manager can regenerate it from the queue; it never overwrites newer product edits. Generating a draft requires an active installation, available platform definition, merchant consent, and the caller's existing sales or production permission. Listing, applying, and rejecting drafts additionally require `employees.manage`. Merchants can revoke consent; pausing the employee also blocks the tools. Other catalog roles remain non-executable until their tools are implemented and published. These employee pilot tools are not billed and cannot run background tasks or operate automatically.

The platform control center includes a request queue for merchant employee applications. Approval and rejection are audited; approval does not grant data permissions or change the employee definition's publication state. The first five vertical roles (Product Manager, Designer, Photo Editor, Writer, and Marketer) are catalog entries only unless their status is explicitly published and their tools are implemented.

The merchant AI Team page includes shared long-term memory for work preferences, brand voice, and operating rules. Owners and authorized store managers can list, create, edit, and delete up to 50 entries (500 characters each); each change is tenant-scoped and audited. Memories are not automatically inferred or saved from conversations. Sensitive-looking email, phone, bank, and credential strings are redacted before storage, but merchants should not enter customer personal data or secrets. Active, authorized Product Manager workflows receive only the current merchant's recent memories as untrusted context; memory can guide phrasing or business context but cannot grant permissions, override tenant isolation, or become product facts. Existing personal preferences for the merchant dashboard assistant remain separate.

The AI Inventory Manager can be published as an available employee and separately authorized with `inventory.stock.read`. Its natural-language query planner may only extract one product name, style number, SKU, color, or size search term. Results come from the authenticated merchant's normalized `InventoryBalance` rows at the configured single warehouse and include on-hand, reserved, available (`onHand - reserved`), in-transit quantities, and the balance update time. The query also requires the related product to belong to the same merchant and be non-archived. The endpoint checks the employee installation and permission again before returning data, answers only from the database results, and does not adjust, reserve, transfer, or order stock. It requires `employees.manage` and is rate-limited. The legacy `Product.inventoryStatus` label is not treated as a quantity.

The AI Sales Manager can be published and separately authorized with `sales.summary.read`. It answers from the authenticated merchant's aggregate order and sales totals for the fixed last-30-day period, including order-status breakdowns; cancelled and returned orders are excluded from overall sales totals. It does not receive buyer identities or contact details and does not return order numbers. The AI Team can run one sales-summary task at a time, and each read is audited. This is a bounded operational summary, not a ShopifyQL-style custom report builder or report-export workflow. The Inventory Manager may also use sales aggregates for replenishment analysis only when both `inventory.stock.read` and `sales.summary.read` are granted; recommendations are read-only and do not create purchase orders or change stock.

The Product Manager can also create a supplier-import draft from one image, PDF, CSV, or XLSX file up to 8 MiB. The original file is parsed in memory and is not persisted or sent to a third-party AI service. Text extraction and image understanding use the configured local Ollama service; image recognition requires a locally available vision model (`OLLAMA_VISION_MODEL`, default `llava:latest`). Extracted fields are validated and saved as tenant-scoped import drafts. A merchant manager must review and complete required fields before creating a product in `draft` lifecycle state; import never publishes a product. PDF/XLSX extraction is bounded and supports a limited set of common document structures, not every supplier template.

The Product Manager supports optional creative generation after the merchant separately grants `product.creative.generate`. The platform administrator selects either a local AUTOMATIC1111-compatible Stable Diffusion WebUI (`LOCAL_IMAGE_GENERATION_URL`, default `http://127.0.0.1:7860`, restricted to loopback HTTP) or the Fal endpoint configured in the AI control center; local generation is the default. Set `LOCAL_IMAGE_GENERATION_MODEL` only to label the local model in the review record. Generated images are decoded, normalized to WebP, and stored in the merchant-scoped `AiEmployeeCreativeDraft` table. The merchant AI Employee page can generate, privately preview, download approved WebP assets, approve, reject, or delete them. Approval only marks the asset approved: it does not attach the image to a product or publish anything. An authorized merchant manager may then explicitly select a merchant product and attach the approved image to its media gallery; this updates only the product's media/images fields. For an already published product, the image may become visible immediately, and the confirmation warns about this. The operation is tenant-scoped, rejects archived products, enforces the gallery limit, and writes an audit event. Rejection clears the stored image bytes. Generation requires the active available Product Manager, explicit merchant consent, and `employees.manage`; the service enforces tenant ownership, a per-merchant draft cap, and rate limiting. Provider failures are surfaced explicitly unless the administrator has opted into local fallback.

`GET` and `POST /api/merchant/ai-employees/:id/tools/creative-drafts` list and create drafts; `GET /api/merchant/ai-employees/:id/tools/creative-products` lists/searches selectable products; `PATCH` and `DELETE /api/merchant/ai-employees/:id/tools/creative-drafts/:draftId` review or remove a draft; and `POST /api/merchant/ai-employees/:id/tools/creative-drafts/:draftId/attach` attaches an approved image to one merchant product. The authenticated private image endpoint is `GET /api/merchant/ai-team/creatives/:id/image`. Every endpoint checks the authenticated merchant and `employees.manage`; generation and product listing additionally check the employee installation and its separate creative permission.

The registry API is protected by platform-admin authentication, the existing admin IP allowlist, and the `settings.ai_support` permission. `GET /api/admin/ai-employees` lists definitions; `PUT /api/admin/ai-employees/:id` updates only the description, version, and lifecycle status; `GET /api/admin/ai-employee-requests` lists pending merchant requests; `PATCH /api/admin/ai-employee-requests/:id` approves or rejects a request. These changes write audit events. Merchant endpoints expose the catalog and only the authenticated merchant's installations; application, pause, and permission-grant actions use the existing tenant middleware, `employees.manage` authorization, and employee audit log. `GET /api/merchant/ai-team/memories` lists the authenticated merchant's shared memories; `POST` creates one; `PATCH /:id` edits one; and `DELETE /:id` removes one. All require `employees.manage` and scope by authenticated `merchantId`. `GET /api/merchant/ai-employees/activity` returns only the latest 50 AI employee event summaries for the authenticated merchant, without audit metadata or prompt contents. `GET /api/merchant/ai-employees/:id/tools/product-catalog` exposes the consent-gated read-only tool; `POST /api/merchant/ai-employees/:id/run` runs the fixed Product Manager workflow; `POST /api/merchant/ai-team/run` runs the constrained AI Manager delegation flow; `POST /api/merchant/ai-employees/:id/tools/product-content-draft` generates and persists a pending proposal; `GET /api/merchant/ai-employees/:id/tools/product-content-drafts` lists the installation's proposals; `PATCH /api/merchant/ai-employees/:id/tools/product-content-drafts/:draftId` lets an authorized manager apply or reject a proposal. Product-import endpoints create, list, and review pending supplier-file drafts. Apply is tenant-scoped, transactional, audited, and uses an optimistic source-content check to prevent overwriting newer edits. The runtime uses the existing local Ollama service (`OLLAMA_BASE_URL`, defaulting to loopback) and the configured `qwen2.5:7b` model. Review the additive migrations and use the normal backup/maintenance procedure before applying them to production; do not run production migrations without approval.

### AI feedback, wholesale approval, and reporting

ModaGPT merchant thumbs-up/down feedback is stored against the assistant message and is editable by the same conversation owner. Feedback captures the preceding redacted user prompt, answer, merchant, context, and timestamp. Platform administrators with `settings.ai_support` can review the most recent 100 entries in **AI 大脑运营中心** through `GET /api/admin/merchant-assistant/feedback`; the endpoint is no-store and admin/IP protected. Apply `20260930150000_add_merchant_assistant_feedback` before using this feature.

In Orders → Draft quotes, an authorized merchant can ask the configured reasoning provider to propose product/SKU quantities for an approved, linked buyer. The model sees only the request and a bounded list of this merchant's published product/SKU candidates; it does not receive buyer names or contacts, set prices, or choose delivery/payment terms. The server validates ownership, buyer eligibility, exact product/SKU identity, MOQ, pack multiples, and computes the buyer-specific unit price from the current wholesale price and buyer discount. The seller must enter confirmed delivery days and delivery/payment terms and explicitly approve the result. Approval transactionally creates an unsent `SalesQuote` draft; it does not send a message, create an order, reserve stock, or change inventory. The seller must choose to copy/send the buyer link; only buyer confirmation converts the quote to an order through the existing quote-confirmation workflow. If buyer eligibility, product/SKU availability, MOQ, pack size, or price changes before approval, the proposal is marked stale and must be regenerated. Rejecting a proposal has no order or inventory side effects. Apply `20260930153000_add_merchant_ai_order_drafts` to add this workflow and the quote terms fields.

The merchant Analytics workspace provides sales and current-inventory previews and CSV exports. Sales filters are an inclusive order-date range (up to 367 calendar days) and an optional exact order status; queries are limited to 5,000 rows and must be narrowed when exceeded. Totals report stored order amount, quantity, and shipping fee separately and do not estimate margin/profit or causal explanations. Inventory is a point-in-time snapshot from the normalized single-warehouse ledger, supports product/style/SKU search, and is not historical stock reporting. Sales access requires `sales.order.create`; inventory access requires `warehouse.pick` or `warehouse.review`. Both exports are tenant-scoped, no-store, and CSV-escape spreadsheet formula prefixes.

### DeepSeek reasoning API

Platform administrators with `settings.ai_support` can select DeepSeek for AI employee reasoning in **AI 大脑运营中心**, add a platform DeepSeek API Key, and use **测试 DeepSeek 首次调用** after saving. The initial model is `deepseek-flash`; `deepseek-v4-pro` is also selectable. The server sends non-streaming requests to the fixed `https://api.deepseek.com/chat/completions` endpoint using Bearer authorization, JSON-object output mode, `thinking: {"type":"enabled"}`, and `reasoning_effort: "high"`. DeepSeek's OpenAI-compatible response is validated and returned to existing AI employee workflows; a failed request uses local Ollama only if the administrator enables fallback. Supplier image recognition remains local and does not send image bytes to DeepSeek. Reasoning prompts and the relevant merchant/product facts included in those prompts are sent to DeepSeek when enabled. The API key is stored separately from the Fal key, encrypted server-side, omitted from API responses and audit details, and can be rotated or cleared in the control center. The connection test sends only a synthetic JSON request and records its result, not the key or completion.

### Fal.ai creative image provider

Platform administrators with `settings.ai_support` can configure the platform Fal API Key and image endpoint in **AI 大脑运营中心**. The key is AES-GCM encrypted in the server-only integration configuration, never returned by the admin API, and never placed in browser configuration. Leave the password field empty to keep the current key; clearing or rotating it is an explicit admin action. The server uses the official `@fal-ai/client` SDK and calls the selected Fal endpoint directly; this Express/Vite application does not expose a generic Fal proxy route. The image endpoint defaults to `fal-ai/flux/schnell`. Fal is currently used for creative image generation only; product reasoning and supplier-image recognition remain on the configured local Ollama service because the Fal LLM/vision examples currently listed by Fal are marked unsupported.

When Fal generation is enabled, the creative prompt and included product/brand details are sent to Fal for processing. A platform administrator may explicitly enable local image-generation fallback. Fal results are downloaded only from HTTPS `fal.media`/`fal.ai` hosts, capped at 8 MiB, checked as supported image formats, then pass through the existing WebP normalization and merchant-scoped draft flow. The image remains private and requires merchant review; Fal integration does not publish or attach it automatically. Confirm merchant notice, privacy, provider terms, and data-retention requirements before enabling external generation. Merchant feature consent, employee permissions, rate limits, audit records, and existing image moderation still apply.

### Merchant platform support

The local RAG library also includes curated general guidance on clothing wholesale, B2B buying, merchant onboarding, store operations, product/SKU data, fulfillment, returns, and fashion-industry basics. Administrators can add up to 100 categorized knowledge articles from the console. Each article is marked either as confirmed RUDA platform information or general industry guidance; general guidance must not be used to infer RUDA-specific fees, approvals, inventory, payments, or case outcomes. Custom articles are persisted in the protected server-side `logs/ai-support-config.json`; embeddings are rebuildable from `logs/merchant-support-knowledge-index.json`.

Merchants can open support conversations from the merchant portal's **平台客服** tab. Platform administrators with the `settings.ai_support` permission can review, reply to, assign, prioritize, and resolve conversations from **商家在线客服**. The assistant runs local Qwen2.5-7B-Instruct through Ollama and uses local `nomic-embed-text` embeddings to retrieve approved FAQ/SOP passages from a persistent vector index. This "training" is retrieval-augmented generation (RAG), not model fine-tuning. The application server must keep Ollama bound to loopback, with `qwen2.5:7b` and `nomic-embed-text` installed; set `OLLAMA_BASE_URL=http://127.0.0.1:11434` if the default differs. The assistant receives only the authenticated merchant's basic business profile and support history as context; credentials, contact details, VAT/banking data, and financial records are not included. High-confidence, low-risk platform questions can be closed as AI self-service; sensitive, uncertain, or unavailable-model cases remain in the human queue with a handoff reason. Human first-response SLAs use calendar hours and default to urgent 1h, high 4h, normal 24h; authorized administrators can adjust these targets. The admin console reports queue volume, overdue work, response-time/SLA performance, AI self-service resolutions, and merchant helpfulness feedback; negative AI feedback can be filtered for human knowledge-base review. The assistant does not automatically modify its own knowledge from ratings. Once an administrator marks a human-handled conversation resolved, a sanitized summary and local embedding can be stored as long-term memory for that merchant alone; merchants and administrators can clear those memories without deleting original conversations. Messages refresh by polling every five seconds; this is not a push-notification channel. Apply the `add_merchant_support_chat`, `add_merchant_support_long_memory`, `add_merchant_support_ai_feedback`, and `merchant_support_enterprise_ops` Prisma migrations before deploying the latest customer-support changes.

The inventory migration introduces normalized product variants, warehouse locations, inventory balances, and append-only inventory movements. It backfills the existing `Product.skus` data during deployment so the legacy UI can remain online while the operations console migrates to the normalized inventory APIs.

The platform currently operates a single physical warehouse (`central`, RUDA 总仓). The single-warehouse migration removes the legacy Mestre/Milano inventory locations and their historical balances/movements; showroom locations remain customer-facing appointment/showroom records, not stock locations.

### Fashion Community scale-up

The Fashion Community migration stores posts, reactions, creator follows, and comments in indexed PostgreSQL tables. In database mode, the app queries feed pages and moderation batches instead of loading every post into process memory. The mobile immersive feed mounts only a small window of cards/videos. Production uploads require S3-compatible object storage and a public CDN base URL so media does not accumulate on the application server.

To migrate an existing installation:

1. Take and verify a PostgreSQL backup; preserve `logs/shared-gallery.json` and `logs/fashion-social.json`.
2. Review all pending migration SQL. `npm run db:migrate` applies every unapplied migration, not only the Fashion Community migration.
3. Run `npm run db:import-fashion-community -- --source-check` to validate the legacy files without database writes. After schema migrations are applied, run `npm run db:import-fashion-community` in check-only mode to compare source and target counts.
4. Run `npm run db:import-fashion-community -- --apply` only after the count and content review passes. The import is transactional, moves embedded/local legacy media to the configured object store, and verifies record counts.
5. Configure `FASHION_COMMUNITY_STORAGE=database` and the production object-storage/CDN variables, then restart the app. Keep the original JSON files and backup until feed, moderation, upload, playback, and delete checks pass.

Do not enable database mode before both the schema and import are ready. Do not run production migrations without an approved maintenance window and verified backup.

### Interface localization

The interface supports `en`, `it`, `zh`, `fr`, `de`, `es`, `pt`, `nl`, `pl`, `ro`, `tr`, and `ar`. Italian and Simplified Chinese are the maintained source dictionaries; other locales are generated from Italian by the configured AI translation provider and cached in the browser. Legacy Italian/Chinese interface copy should use `localizeCopy(zh, it)` so it can be translated and cached instead of selecting Chinese for every non-Italian locale. Translation failures are logged and surfaced to the user, with Italian as the single-language fallback; AI-generated wording is not authoritative and must not be used as an unreviewed source for fees, platform policy, legal terms, or order commitments. Product and merchant catalog fields remain business data and require their own approved localized values.
