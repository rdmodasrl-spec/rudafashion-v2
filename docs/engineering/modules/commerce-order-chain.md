# 模块规格：智能订单链

- Module ID：`commerce-core`（现有商品订单交易域，不新增平行订单模块）
- 模块状态：部分完成
- 文档阶段：开发中
- 日期：2026-10-24
- 对应负责人/团队（如适用）：产品、前后端与测试共同维护

## 1. 背景与问题

现有 B2B 订单已使用共享 `Order` / `OrderItem`、支付流水和多包裹履约记录，但商家确认、付款、备货、发货及签收仍主要由若干独立状态和页面操作驱动。订单详情需要成为双方共用的履约入口，并基于双方确认的同一交易条件版本计算下一项任务。

本规格记录智能订单链的目标行为及实施边界；当前代码与目标尚有差距，不表示端到端功能已完成。

## 2. 目标与非目标

### 目标

- B2B 买家与商家通过同一权威订单记录查看相同进度、已生效条款及事件。
- 固定显示五个主阶段：待确认、约定确认中、处理中、运输中、已送达/已完成。
- 每个参与方的订单详情只突出一个当前任务；仅在该任务要求人工输入时显示表单。
- 每次关键条款变更创建不可变版本；同一版本需买卖双方均确认才生效。
- 付款、供货、分批履约分别持久化；当前任务按生效条款和真实业务事件推导，不强制统一付款/发货顺序。
- 复用现有 SKU 订单明细、支付流水、履约包裹、物流事件、权限和通知能力。
- 不允许库存不足但允许订货的 SKU 被现货数量限制；按 SKU 保留现货/订货分配。

### 非目标

- 不改版、重做或迁移无关后台模块、身份认证、支付服务商和商品目录。
- 不另建订单主表、支付系统、通知系统或物流系统。
- 不声称已有承运商实时 GPS / ETA 集成；无可靠数据时仅显示最近记录及更新时间。
- 本阶段不扩展为独立的 B2C 零售订单系统；`ConsumerOrder` 前端状态及 `/api/consumers/me/orders` 调用需另行核实，不能与 B2B `Order` 混为同一数据源。

## 3. 现状审计与防重复检查

- 已检查源码、路由、数据模型、测试与文档：`server.ts`、`src/api/client.ts`、`src/context/B2BContext.tsx`、`src/types/b2b.ts`、`src/apps/shared/components/frontend/OrdersView.tsx`、`src/apps/merchant-admin-web/MerchantPortal.tsx`、`src/apps/merchant-admin-mobile/MerchantMobileApp.tsx`、`merchant-miniprogram/pages/orders/`、`miniprogram/pages/checkout/`、`miniprogram/utils/api.js`、`prisma/schema.prisma`、订单/履约相关迁移和 `tests/`。
- 关键字/目录：`/api/orders`、`/api/merchant/orders`、`/api/*/shipments`、`Order`、`OrderItem`、`PaymentTransaction`、`FulfillmentShipment`、`ShipmentTrackingEvent`、`calculateOrderSupplySplit`。
- 已有权威能力：
  - `Order`、`OrderItem` 是 B2B 订单和逐 SKU 明细来源；订单通过 `/api/orders` 创建、买家经 `/api/orders` 读取、商家经 `/api/merchant/orders` 读取。
  - `PaymentTransaction` 与现有支付路由记录收款；银行转账核实已有独立商家权限检查。
  - 新协议只接受当前协议付款 API 可结算的银行转账与银行卡方式；PayPal、Solana、现金、账期等方式未接入此协议支付闭环，不允许新约定选用。
  - `FulfillmentShipment`、`FulfillmentShipmentItem`、`ShipmentTrackingEvent` 支持订单多包裹、逐 SKU 发货数量及轨迹。
  - `src/server/orderSupplySplit.ts` 按现货和 SKU 订货许可拆分数量；使用 `src/api/client.ts` 及现有租户/员工权限中间件。
  - 商家 Web、商家手机后台及商家微信小程序已有订单和履约界面；买家 Web/手机和微信小程序复用现有订单 API。
- 现有方案不足：交易条款尚无不可变版本及双方逐版本确认模型；订单详情仍需从订单/支付/包裹多处状态判断操作；支付和发货前置条件存在硬编码；物流事件未见统一数据来源/同步元数据契约。当前检索未发现订单承运商自动追踪集成。
- 新建边界：仅在现有 `commerce-core` 下扩展约定/事件数据和共享状态推导；继续使用 `Order` 作为唯一主订单、现有支付与履约表作为其子记录。不能新建第二套订单 API 或客户端状态权威源。

## 4. 归属与边界

- 所属业务域：`commerce-core` 商品订单交易。
- 使用运行面：前台 Web/手机、商家后台 Web/手机、买家微信小程序、商家微信小程序，以及共享订单 API。
- 模块负责：B2B 订单交易条款版本、双方确认、当前任务判定、付款/供货/包裹状态汇总及其订单详情展示。
- 模块不负责：商品定价权威、库存账本、收款服务商执行、身份认证、通用通知投递及承运商服务提供的事实数据。
- 数据权威：PostgreSQL/Prisma `Order` 与既有支付、履约记录；客户端缓存只作展示。
- 入口：买家 `OrderCenterView` / `OrdersView` 与小程序订单页；商家 `MerchantPortal`、商家手机后台与商家微信小程序订单页。

### 商家 Web 订单工作区

- 商家 Web 订单工作区固定为订单列表与订单详情两个主要视图；订单链处理继续复用同一订单详情，不为审核、协商、付款、备货、发货或物流拆出新页面。订单列表字段为客户（名称及国家）、商品（名称、件数及 SKU 规格数）、金额（总额及已付/未付/部分）、当前状态、商家待办、操作。桌面使用紧凑表格，窄屏使用同字段的卡片布局。
- 列表筛选采用“全部、待我处理、进行中、物流异常、已完成”。桌面复用顶栏全局搜索作为订单搜索入口，不重复显示列表搜索框；全局搜索订单时支持订单号、客户、SKU/商品及物流信息，查询会同步筛选当前订单列表。手机端顶栏搜索不可见时，在订单列表保留唯一搜索入口。订单列表主工具行保留五个状态筛选、日期范围、独立主操作“＋开单”和导出订单。不重复展示“订单”页面标题或“订单/草稿报价”切换行；不显示“更多筛选”入口、订单/草稿报价数量徽标、订单分析图表或重复汇总卡。每笔订单只提供一个“操作”菜单按钮，菜单内为打印、开票和发送；不在行内展开重复操作按钮。
- “＋开单”进入现有独立新订单表单页，提交仍复用正式订单创建 API 并进入现有订单链，不跳转 Smart POS。页首为“创建订单”与返回按钮，底部固定“返回修改｜创建订单”。复用商家客户 API 登记新客户；支持搜索已关联客户及商品、多个商品与多个 SKU。颜色/尺码/价格均读取服务端商品 SKU；允许缺货订货，不依据现货限制采购数量；MOQ/箱规按商品汇总校验。展示逐 SKU 数量/小计、件数、商品金额、运费、其他费用及总额；任何额外费用和价格例外须走具权限的服务端校验与审计，不采信客户端价格。允许使用客户档案现有默认地址或填写本次地址，并必填收件人、联系手机/电话及完整配送地址。商家填写的付款/供货约定只作为商家提案，新订单不得预确认客户或启用付款/履约。
- 新客户资料通过现有 `Customer` 与 `MerchantCustomerLink` 权威模型建立，保存为待审核/待绑定；不得伪造买家账号或确认。账户绑定只通过现有买家邮箱验证码注册流程：商家可触发已有验证码请求，只有邮箱所有者通过验证码注册后，服务端才将买家 `AuthAccount` 安全关联到唯一匹配的待绑定 `Customer`；同邮箱存在多个候选资料时拒绝自动绑定并走人工核验。无账户客户可以被关联订单，但订单保持 `pending_buyer`，直到该客户通过安全流程完成账户绑定后才可确认。发送通知不等于身份验证或客户同意。
- 使用现有商家订单认证权限创建正式 `Order`、SKU/价格与现货/订货拆分快照、交易约定 v1 和订单链事件，记录来源 `merchant_assisted_order`、操作者和创建时间；协议最终生效时按当前 SKU 现货与订货规则重新核对拆分。通知客户查看订单。创建成功刷新原订单列表并直接打开该订单现有详情浮层/聊天，不新建详情页、聊天或状态管理。不得使用 POS/员工即时销售接口，不得扣减/预留库存，不得创建支付流水或包裹。API 使用商家租户隔离、权限校验及幂等键，服务端验证客户关系、商品归属、SKU、MOQ/箱规、数量、价格、金额、收件信息和条款。

#### 代客下单数据与身份绑定契约

- `Customer` / `MerchantCustomerLink` 仍是客户资料及商家关系的唯一来源；新增客户沿用 `POST /api/merchant/customers`，不创建访客或代客专用客户表。新资料需真实联系人、电话、有效邮箱、企业及地址；身份尚未绑定时显式标记并继续走现有验证码账户注册。
- 扩展现有 `/api/auth/register/quick/request` 与 `/api/auth/register/quick/verify`：验证码校验成功后，如尚无买家账号且存在唯一同邮箱客户资料，则创建买家 `AuthAccount` 指向该既有客户，不新建重复 `Customer`；若已有未关联客户档案的买家账户，必须再校验账户密码后才关联。多个候选匹配必须拒绝并审计。普通未匹配邮箱保持现有快速注册行为。已由商家预登记的邮箱不得通过未验证邮箱注册接口绕过验证码绑定。
- 扩展现有 `Order`、协议快照与序列化以保存收件人、收件电话、额外费用金额/说明；金额仅在订单/协议中计算一次。额外费用默认为 0，客户协议确认仍是所有付款、备货/发货授权的前置条件。
- 代客创建 API 仅允许与当前商家有关联且状态为 `pending` 或 `approved` 的客户；`rejected` 客户不可下单。客户未绑定账号时订单可保存并通知其档案邮箱，但前端须明确标记待账户绑定；不得将邮件发送记作买家确认。绑定后买家使用既有订单详情、约定确认与聊天 API。
- 建立流程测试：独立页面而非弹窗、返回保持表单、商品/客户搜索、混色混码订单汇总 MOQ 与阶梯价、低库存仍可订货、费用总额不重复、完整收件人校验、待绑定客户的安全关联/多匹配拒绝、双方确认前不激活、幂等重放以及创建后打开现有订单详情。

### 商家代客下单 API 契约

- `POST /api/merchant/orders/assisted-create`：仅商家租户下具有 `sales.order.create` 权限的员工可调用；客户必须为 `pending` 或 `approved` 且与当前商家存在订单、看货申请或客户关联记录。未绑定账户的客户必须有可用邮箱；已绑定客户可使用现有账户访问订单。商品必须归属当前商家且为已发布商品。
- 请求：`customerId`、`idempotencyKey`、`items[]`（`productId`、`sku`、正整数 `quantity`）、完整 `shippingAddress`（必填 `recipient`、`phone`、`street`、`city`、`country`、`zip`）、`shippingFee`、`additionalFees`、有额外费用时的 `additionalFeesDescription`、以及商家提案 `terms`（付款方案、付款方式、预付款金额或比例、余款触发条件/日期、自定义付款条件、供货方式、预计交期）。客户端价格不被接受；服务端依据商品批发价、商品数量阶梯价和客户折扣重算金额，按 `商品金额 + 运费 + 其他费用 - 折扣` 计算一次总额，并检查 MOQ、箱规、SKU、商品权限及费用。
- 成功响应：`201 { success, order: { id, orderNo, totalAmount }, agreement: { id, version, status } }`；相同幂等键与相同请求重放返回既有订单及 `idempotentReplay: true`；相同键不同请求返回 `409 IDEMPOTENCY_KEY_CONFLICT`。
- 错误：输入格式/约定无效返回 `400`；客户/商品/SKU 不可用、客户无可绑定邮箱、订货不受 SKU 规则允许、MOQ/箱规错误、价格异常或金额不成立返回 `409`；未认证/无权限由既有中间件返回统一认证/授权错误；未预期服务端错误通过标准内部错误处理器返回。
- 一次数据库事务创建待确认 `Order`、SKU 明细及现货/订货拆分快照、商家已确认而客户待确认的 `OrderAgreementVersion v1` 及 `order.created` / `agreement.proposed` 事件。成功后通过现有通知队列通知客户确认。创建时不写支付流水、库存预留、库存账本、POS 销售或包裹记录；客户确认协议前不授权付款/履约。
- 验收：提交后刷新原订单列表并直接打开同一订单详情浮层；重复提交不重复创建；无商家权限、跨租户客户/商品、无效 SKU、MOQ/箱规不符及无效地址均失败；数据库库存、支付和包裹记录保持不变。上线前还需对真实数据库 schema、通知队列和买家确认入口执行集成验证；不得把静态构建通过当作端到端验收。
- 详情顶部呈现订单号、状态、关闭操作及唯一主进度线；桌面端为居中浮层，宽度约视口 86%–92%（最大 1440px）、高度约视口 88%–92%，列表保留在半透明遮罩下。浮层内部左侧约 65% 为当前任务/订单信息，右侧约 35% 为订单沟通区；窄屏改为接近全屏单列布局，聊天可折叠。浮层独立滚动，关闭或浏览器返回后恢复原列表状态和滚动位置。当前任务始终展开；已完成条款、付款、包裹和历史记录按需折叠，运输阶段重点展示物流。
- 视觉采用白底、黑色主操作、浅灰辅助区域及细分隔线；不使用宣传语、渐变装饰或重复说明。
- 临时生产演示订单必须以 `[RUDA_DEMO]` 标记，且不得伪装成真实客户业务。演示数据清理后，订单列表不显示演示订单；清理仅限明确授权的演示订单及其 SKU 明细，不触碰真实订单或客户业务记录。
- 买家 Web/手机订单详情与商家 Web 订单详情共用同一订单聊天面板/API；窄屏聊天可在当前订单内折叠，不跳转独立消息页。微信小程序调用同一 API 的界面接入不在本次商家 Web 工作区实施范围内，仍需后续端侧验收。
- **商家手机订单统一工作区：** 继续使用唯一的 `merchantOrders` 数据集和 `/api/merchant/orders`，同一列表混合展示批发订单及 POS 销售，不另建 POS 列表。顶部显示“订单”和“＋开单”，摘要只用真实数据统计待处理、进行中、待收款；搜索订单号、客户、商品名称和 SKU；筛选为全部、待处理、进行中、已完成。订单项展示客户、商品/件数、金额/付款状态、订单状态/当前任务和来源短标签；POS 来源按现有 `POS-` 订单号识别，批发订单不按相似状态伪装 POS。
- 手机“＋开单”只弹出批发开单 / POS 销售两个选项。批发流程在手机端接入本规格已有的 `/api/merchant/orders/assisted-create`，提交后刷新同一列表并直接打开所建订单；不调用会即时出单的 `/api/merchant/employee-orders`，不扣减/预留库存，不越过客户对协议 v1 的确认。POS 则复用 `MerchantSmartPos` 现有商品、客户、班次、付款确认、库存和幂等提交规则；完成后刷新同一订单数据并返回该订单详情。不开第二套商品/客户/订单数据，不增加旁路状态机。
- 草稿能力盘点（实现前）：当时没有商家批发订单草稿 API；POS 只有真实销售提交。用户已批准扩展现有 `Order` 流程，当前已实现下述持久化草稿；不能把草稿表单数据当作正式订单或客户确认。
- **已确认的服务端草稿方案：** 用户批准实现持久化批发草稿。仍以 `Order` 为唯一订单事实来源：新增可空 `assistedDraftData` 字段，仅用于 `status='draft'` 的商家辅助开单；草稿保存在现有 `Order` 行中，使用 `DR-` 草稿编号和现有幂等键。`POST /api/merchant/orders/assisted-drafts` 创建、`PUT /api/merchant/orders/assisted-drafts/:id` 更新，均须商家租户与 `sales.order.create` 权限；只有该商家可读取/更新。草稿不可被买家查询、聊天、确认或付款，不触发客户通知/库存/支付/包裹/结算记录。提交时调用已有 `/api/merchant/orders/assisted-create` 并传 `draftId` 与相同幂等键，服务端在单一事务内校验现有完整规则、生成协议 v1/事件和明细，将同一 `Order` 行转为正式 RU 订单，不创建第二笔订单；失败时原草稿及字段保持不变。草稿内容限长、结构化验证并只允许存储当前商家关联客户及本商家的已发布商品/SKU 引用；价格在正式提交时仍由服务端重新计算。新增 nullable 列迁移不回填旧订单；回滚代码时保留该列与草稿记录，生产迁移/发布仍需单独授权。
- 手机订单详情为接近全屏、原列表留在下层的单一页面类型，关闭后回到原订单和筛选/滚动位置。顶部显示订单号、批发/POS、金额及状态；主区域只保留一条主进度线和一项当前任务；其后按序显示订单内 1 对 1 聊天入口/折叠面板、商品明细、交易约定、付款记录、发货与物流。详情不跳到客户、POS、财务或其他工作区。聊天复用 `src/apps/shared/components/common/OrderChatPanel.tsx` 及现有订单专属 API；ModaUI 助手继续独立，不注入聊天。条款、付款及物流未展开时不常驻展示长说明；付款状态以服务端记录为准，物流仅显示已记录的包裹/轨迹事实。POS 销售完成状态不虚构运输阶段或包裹。
- 手机主导航只显示首页、商品、订单、更多；智能助手继续由首页/更多现有入口独立打开，不与订单聊天合并。
- **当前实现盘点（原审计结论已过时）：** `MerchantMobileApp.tsx` 与 `MerchantMobileOrderWorkspace.tsx` 现提供统一订单主页、批发/POS 入口和单一订单详情；订单数据仍来自现有商家订单 API。POS 继续调用 `/api/merchant/employee-orders`，批发草稿使用同一 `Order` 表及新的草稿 API，正式提交时转成同一订单并调用既有约定流程。订单详情复用 `OrderChatPanel`、现有消息/支付/物流记录。颜色/尺码、客户及商品使用既有后台数据；草稿金额在正式提交时由服务端重新核算。
- **本轮验收（本地代码验证）：** 商家手机构建成功；`prisma validate`、`prisma generate` 通过。草稿解析、租户隔离与导航定向测试共 13 项全部通过。手机工作区定向 TypeScript 检查通过；纳入 `server.ts` 的定向检查仅报告现有 `WechatMessagePushVerification` 联合类型问题（server.ts:5448、5464），未报告本轮新增代码类型错误。全仓 `npm run lint` 因 Node 堆内存耗尽未完成。手机浏览器视觉、真实商家会话、数据库集成及客户通知/确认闭环尚未验收；迁移尚未应用，不得视为已发布。

### 订单智能聊天

- 智能处理只发生在既有订单聊天 POST 流程中；不新增聊天窗口、会话、客户支持模块或 AI 第三方参与者。常见订单事实由服务端基于当前已授权订单、成功支付/退款流水和包裹轨迹生成确定性答复，并持久化为来源 `automatic`、角色 `system` 的订单消息，界面标注“自动回复”。
- 已检查的 `src/server/merchantSupportAi.ts` 面向商家工作台知识问答，使用 Ollama/RAG；`/api/ai/support/chat` 的订单问答是买家全局助手的订单列表摘要。两者均不是订单上下文隔离的聊天服务，不得把当前订单支付、退款或地址等隐私事实交给通用模型。故本功能复用既有订单 API、认证、消息模型和通知投递，不调用模型生成订单事实答复。
- 只自动回答明确的事实类问题：订单阶段/当前任务、已记录付款和退款汇总、商品数量/订单金额、备货/发货情况及最近一条已记录物流事件。物流答复注明“最近记录”和时间；没有记录则明确告知暂无，不推断 GPS 或预计送达。
- 议价、折扣、改数量/价格/付款/交期/发货条件、提前发货、退款、投诉、争议及不能可靠归入事实问答的问题，保留原买家消息并标记 `requiresMerchantReply`；通过现有 `NotificationEvent` 为所属商家创建幂等站内提醒，邮件提醒只沿用现有通知配置。商家真人消息关闭其之前的待回复标记。AI 不提出或应用交易条款。
- `OrderMessage` 增加 `source`（`human` / `automatic`）、`requiresMerchantReply`、`merchantRepliedAt`、`replyToMessageId`；自动答复用 `senderRole=system`、空 `senderId` 表示系统生成事实答复，不代表增加第三个聊天参与者。`replyToMessageId` 唯一，确保同一客户消息最多一条自动答复；原客户端 UUID 继续确保用户消息提交幂等。
- 买家和商家仍只可访问各自订单的全部消息。商家以 `Order.merchantId` 为唯一聊天归属；仅对该字段为空且所有订单商品都归同一商家的旧订单，才按唯一商品商家兼容访问，其他商品商家不得读取、发送或收到提醒。自动答复及人工消息均以同一订单外键持久化，排序/轮询/刷新行为一致；系统消息对买家读取时标记已读，买卖双方订单列表分别统计对方未读消息。待商家回复标记和站内通知独立于消息已读状态。
- 集成验证必须在显式隔离的本地 PostgreSQL 测试库运行，测试 migration、API 权限、事实答复、升级提醒、重复提交、自动答复唯一性、消息留存及商家回复解除提醒。禁止把应用/生产数据库 URL 当作迁移目标。

### 订单消息数据与 API 契约

- 权威数据继续归属现有 Prisma `Order`；新增 `OrderMessage` 子记录，字段为 `id`、`orderId`、`senderId`、`senderRole`（仅 `buyer` / `merchant`）、`content`（1–2000 字符纯文本）、`clientMessageId`（客户端 UUID 幂等键）、`createdAt`、`readAt`。`orderId` 外键级联删除；按 `(orderId, createdAt, id)` 建立读取索引，按 `(orderId, senderRole, readAt)` 支持未读查询，`(orderId, clientMessageId)` 唯一。
- `senderId` 取自现有认证身份：买家为已认证 `customerId`，商家为当前有效员工 ID；无员工身份时使用所属 `merchantId`。角色由服务端认证上下文决定，拒绝客户端指定发送人或角色。商家租户须拥有订单或其订单商品；买家须与订单 `customerId` 完全匹配。消息内容仅作沟通，不会修改交易约定、付款或履约状态。
- 买家接口：`GET /api/orders/:id/messages?before=<cursor>&after=<cursor>`、`POST /api/orders/:id/messages`、`POST /api/orders/:id/messages/read`；全部要求 `requireBuyerAuth` 和订单所有权校验。
- 商家接口：`GET /api/merchant/orders/:id/messages?before=<cursor>&after=<cursor>`、`POST /api/merchant/orders/:id/messages`、`POST /api/merchant/orders/:id/messages/read`；全部要求既有商家租户身份、订单权限及订单归属校验。列表 `GET /api/merchant/orders` 为每笔商家订单返回 `unreadMessageCount`，未读定义为客户发送且 `readAt` 为空。
- 首次读取按服务端时间及消息 ID 递增返回最近最多 100 条，并给出更早记录游标；`after` 轮询返回游标之后的新记录。打开订单/聊天时调用 read 接口，把对方未读消息标记为已读；不会把自己发送的消息算作未读。
- 发送请求 `{ content, clientMessageId }`；成功响应包含服务端持久化消息。唯一幂等键使网络重试/重复提交返回同一条记录，不重复落库。校验空白内容、超过 2000 字符、无效 UUID，分别以 400 错误响应；订单不存在或不属于当前身份返回 404，不泄露其他租户订单存在性。发送操作沿用服务端限流中间件，超限返回 429。
- 前端每 3 秒使用最近消息游标轮询；请求失败展示错误并允许重试。消息仅在 POST 成功后进入已发送列表，未发送草稿可保留供用户重试；空状态明确显示“暂无消息”。轮询与读取使用统一 `src/api/client.ts`，不添加 WebSocket、假数据或第二套认证/投递机制。
- 迁移只新增表、外键和索引，不改旧订单数据；回滚只在确认未保留需审计的消息记录后，经单独批准删除该表。生产迁移与部署不属于本任务授权范围。

## 5. 用户角色与权限

- 买家：仅能访问 `customerId` 属于当前 `requireBuyerAuth` 身份的订单并确认商家提出的条款版本。
- 商家员工：仅访问其租户拥有的订单/订单明细，并通过既有 `requireMerchantTenant`、员工权限中间件执行审单、提案、收款核实和履约操作。
- 管理员：沿用当前管理员订单路由及权限，不新增旁路。
- 所有写入由服务端校验订单归属、有效条款版本、角色确认状态、金额/数量边界和允许的状态转换。前端权限只用于交互呈现，不作为安全边界。
- 关键确认、付款核实、包裹变更需记录操作者和服务端时间；第三方事件保存其来源。

## 6. 用户流程与状态机

### 正常流程

1. 买家提交订单和初始条款版本；订单保持待确认，不触发未获双方确认的付款或发货授权。
2. 商家接受同一版本，或提出新版本；任何关键字段变化均生成新版本并等待另一方确认。
3. 同一版本完成买卖双方确认后锁定为当前生效版本，系统按约定解锁一个付款、备货/供货或发货任务。
4. 支付回调/到账核实、供货更新、创建包裹和承运商/手动轨迹事件分别更新其子状态及订单事件。
5. 所有包裹送达后，若仍有应付款则显示“已送达·待结款”；仅在全部约定义务满足后完成订单。

### 状态与允许转换

| 当前状态 | 操作/事件 | 目标状态 | 服务端校验 | 失败处理 |
|---|---|---|---|---|
| 待确认 | 商家接受相同条款版本 | 约定确认中/生效 | 订单租户归属、版本号和条款快照一致 | 冲突返回，不改变订单 |
| 待确认/协商中 | 商家或买家提出关键条款修改 | 等待对方确认 | 创建新版本；旧版本只读 | 校验错误返回字段级错误 |
| 等待确认 | 对方确认指定版本 | 生效 | 参与方身份、版本仍为当前提案、金额/数量合法 | 过期/重复确认返回冲突或幂等结果 |
| 条款生效 | 支付服务成功/人工核实到账 | 按协议推进付款状态 | 真实支付交易或授权核实；不可用客户端声明到账 | 保留待核实状态并可重试 |
| 条款生效 | 创建/更新包裹、收到物流事件 | 处理中/运输中/已送达 | SKU 数量不超未发数量、商家租户归属、来源可追溯 | 事务回滚并返回冲突 |
| 所有包裹送达 | 应付款结清/义务满足 | 已完成 | 依据生效版本重算所有义务 | 有未结义务时保留待结款 |
| 未完成订单 | 取消/退款/售后 | 专属处理状态 | 复用现有取消/退款/售后规则 | 记录原因、操作者和结果 |

### 异常流程

- 无权限/跨租户：拒绝请求，不返回订单内容。
- 版本并发：采用条件更新/事务；旧版本确认返回冲突，当前版本不被覆盖。
- 支付失败或转账未核实：保留当前付款任务；上传凭证不等于到账。
- 物流无 API：标记手动来源并链接承运商官方追踪页；显示最后更新时间。
- 包裹异常/停滞：按真实事件生成待处理任务；正常轨迹不需要人工反复确认。

## 8. API 契约

- 复用：`POST/GET /api/orders`、`POST /api/orders/:id/payment`、`GET /api/orders/:id/shipments`、`GET/POST /api/merchant/orders`、既有商家履约/付款核实/包裹 API。
- 需扩展订单序列化结果，统一返回当前进度、活动约定版本、付款/供货摘要和历史事件；当前任务由共享状态推导器按买家/商家角色分别返回，避免 Web 与小程序各自计算；敏感字段按角色过滤。
- 新增 `POST /api/merchant/orders/:id/agreements` 和 `POST /api/orders/:id/agreements` 创建新提案；仅允许买家或该订单商家提交。客户端传入当前 `agreementId` 作为乐观并发条件；服务端在事务内验证版本仍为最新且仍等待当前角色，冲突返回 `AGREEMENT_VERSION_CONFLICT`。提案可包含现有 SKU 的数量/单价、付款计划、供货/分批发货方式、收货/发货条件、运费和预计交期。
- 新增 `POST /api/merchant/orders/:id/agreements/:agreementId/confirm` 和 `POST /api/orders/:id/agreements/:agreementId/confirm` 确认指定版本。重复确认返回既有确认结果；只有同一版本的双方确认齐全才激活。
- 对 `remainingBalanceTrigger=custom`，商家通过 `POST /api/merchant/orders/:id/agreements/:agreementId/trigger-balance` 明确核实自定义条件并填写依据；服务端仅接受当前活动版本、未结余款和有权限的商家操作，写入订单事件后才解锁付款。重复调用返回相同触发结果；这表示人工核实，不表示外部事件自动监控。
- 订单读 API 返回当前条款版本及确认状态。条款快照包含付款计划、首付款/余款条件、现有 SKU 明细、供货/分批发货方式、地址/配送条件、预计交期、运费、币种和由服务端核算的订单金额。买家确认后，在同一事务中应用该版本的 SKU 数量/价格和汇总金额；客户端提供的总金额不作为权威值。
- 买家/商家订单列表返回按成功收款减成功退款核算的 `paidAmount`；有生效约定时附带服务端推导的 `paymentAmountDue`。付款接口只在约定已生效且当前主状态允许付款时处理；运费前置门槛按预备货/发货分别检查。
- 主要错误：`ORDER_NOT_FOUND`、`ORDER_FORBIDDEN`、`AGREEMENT_VERSION_CONFLICT`、`AGREEMENT_CONFIRMATION_REQUIRED`、`ORDER_PAYMENT_NOT_DUE`、`ORDER_NOT_READY_FOR_FULFILLMENT`、`INVALID_ORDER_TERMS`。
- 不新增认证方式；速率限制、幂等、日志与兼容按现有 API 约定核验。写入成功后才触发既有通知；通知不得由客户端伪造。

## 9. 数据与持久化

- `Order` / `OrderItem` 继续为订单和 SKU 数量权威来源；现有 `inStockQuantity`、`preorderQuantity` 用于供货分配。
- `PaymentTransaction` 为支付流水；订单付款汇总与退款仍由既有交易逻辑维护。
- `FulfillmentShipment` / `FulfillmentShipmentItem` 为包裹及包裹 SKU 数量权威来源；`ShipmentTrackingEvent` 为轨迹事件来源。
- 为满足双方版本确认和追溯，新增不可变订单条款版本及版本确认记录（订单外键、单调版本号、条款快照、提议方/时间、每一方确认人/时间）；被确认的条款和 SKU 更新在同一事务应用，可变订单字段不得替代历史快照。
- 订单事件记录需含事件类型、操作者/来源、发生时间和必要的前后快照；不复制商品、付款或物流权威数据。
- 迁移必须 additive，旧订单按 legacy 方式只读兼容；无历史共同确认事实时不得伪造双签。迁移前备份由发布流程执行；回滚先回退兼容代码，不删除新表中已写入的审计数据。

## 10. 集成与事件

- 支付：复用现有 PaymentTransaction 与支付 provider/webhook。只接受服务端确认/人工核实的结果。
- 库存/订货：复用现有 SKU 和库存账本、`calculateOrderSupplySplit`；订单采购数量不以现货上限限制，SKU 不允许订货时按既有规则拒绝或提供协商版本。
- 履约/物流：复用现有多包裹 API 和 `ShipmentTrackingEvent`。仅当可靠承运商接口已配置时自动同步；否则手动事件必须标记来源和时间。
- 通知：复用 `enqueueNotification` 与 `NotificationEvent`，仅对对方有待办或关键状态变化发送，并确保幂等。
- 事件和操作以数据库事务成功为前提；异步通知失败需保留失败状态并由既有投递机制重试。
