# RUDA 商家端全站 UI 整改台账

- Module ID：`merchant-admin-ui-audit`
- 模块状态：部分完成
- 文档阶段：开发中
- 日期：2026-10-25
- 对应负责人/团队：RUDA 商家端产品与工程

## 1. 背景与目标

商家端页面需要逐页改进信息层次、密度、对齐、阅读和操作体验。保持现有 RUDA 中性黑白视觉、真实业务数据、路由和功能；不以批量换文案、单独优化首页或统一套模板替代逐页设计。

## 2. 范围与非目标

### 范围

- 商家后台 Web、商家后台移动 Web，以及仓库中存在的商家微信小程序。
- 逐项覆盖主视图、嵌套工作区、详情、抽屉、弹窗、加载/空/错误状态与操作面板。
- 每页记录设计检查、交互检查、运行/视觉证据及剩余问题。

### 非目标

- 本阶段不以 App Store 业务闭环为重点，不增加其功能。
- 不改 API、数据库、权限、状态机、业务计算、路由含义或生产配置。
- 不使用演示数据，不修改生产数据库。商家 Web UI 的发布仅在用户明确要求后进行，其他运行面不随之发布。
- 除修复范围明确且安全的 UI 缺陷外，不重写业务逻辑。

## 3. 现状审计与复用

- 已阅读 `AGENTS.md`、`docs/engineering/architecture.md`、`docs/application-boundaries.md`、`docs/engineering/module-registry.md` 及模块规格模板。
- 已核对商家入口：`src/apps/merchant-admin-web/main.tsx`、`src/apps/merchant-admin-mobile/main.tsx`；主视图分别由 `MerchantPortal.tsx`、`MerchantMobileApp.tsx` 内的状态与条件渲染决定；小程序页面以 `merchant-miniprogram/app.json` 注册。
- 已检查当前工作区：已有商家端源码、共享组件、文案整改文档和小程序目录均包含未提交改动。只在目标页面整合修改，不重置、不覆盖无关修改。
- 复用既有 RUDA 样式、共享业务组件、`B2BContext`、API client、现有路由与数据源。单页可复用既有组件，但必须独立检查页面实际呈现。
- 本阶段没有新增服务、数据模型、权限或 API，不创建第二套业务/组件系统。
- 本地 Vite 预览需使用 `/merchant?ruda-app=merchant-admin-web`：根路径虽可选择商家应用，但管理引导根据 `/merchant` 路径确定门户区域；否则会停留在加载态。Vite 单独预览不提供 Express API，认证/数据请求会返回 404。已能本地加载商家登录入口，但没有有效本地商家会话与 API，因此不得把经营主页、商品目录或详情状态记为视觉验收通过。

#### 商家手机商品页头部与两层筛选契约（2026-10-26）

目标：商品页头部为固定四行，商品列表独立滚动；筛选分两层，互不替代且不产生重复商品或重复计数。

| 层 | 控件 | 取值 | 数据口径 |
|---|---|---|---|
| 第一行 | 标题 + 上传商品 | — | 上传入口沿用现有商品创建向导 |
| 第二行 | 搜索 | 款号、商品名称（含中/意名）、SKU、条码、颜色、尺码 | 对当前权限范围内商品做包含匹配 |
| 第三层（快捷筛选） | 商品 / 低库存 / 新款 / 已售出 | `all` / `low_stock` / `new_arrival` / `sold` | 商品=当前商家权限内全部商品数；低库存=`isLowStockProduct`（SKU 在手库存合计 < `PRODUCT_LOW_STOCK_THRESHOLD`=20）；新款=`createdAt` 在最近 30 天内；已售出=真实订单成交明细净售出件数 > 0 的商品（与库存多少无关） |
| 第四层（业务分区） | 现货 / 折扣 / 授权 | `getProductZone` 的 `new` / `clearance` / `private` | 一件商品只归属一个分区，三区数量之和等于商品总数 |

- 两层关系为“与”叠加：分区决定商品归属范围，快捷筛选在该范围内收窄；搜索与类目筛选同样为“与”。
- 规则实现集中在 `src/shared/merchantProductBrowse.ts`（`isNewArrivalProduct`、`matchesMerchantProductSearch`、`countMerchantProductQuickFilters`、`countMerchantProductZones`、`filterMerchantProducts`），商家手机页只做展示与状态；低库存阈值来自 `src/shared/productInventory.ts` 的 `PRODUCT_LOW_STOCK_THRESHOLD`。
- 「已售出」数据契约：`GET /api/merchant/products/sales-summary`（`requireMerchantTenant` + 与商品列表相同的 `sales.order.create` / `production.report` / `product.publish` 任一权限）。响应 `{ success, count, totalSoldUnits, products: [{ productId, soldUnits, orderCount, lastSoldAt }] }`，`count` 为有净成交的商品数，`soldUnits` 为净售出件数。查询只用 `OrderItem` 成交明细与 `ReturnRequest` 退货明细，不新建统计表或缓存，也不读取 `Product.inventoryStatus` 文本。
- 「已售出」口径（`src/server/merchantProductSales.ts` → `summarizeMerchantProductSales`）：排除 `draft`、`cancelled` 订单；排除整单退款（`paymentStatus=refunded` 或 `refundStatus=completed`）；扣减 `ReturnRequest.status ∈ {received, refunded}` 的明细件数（按订单 + 商品 + SKU 封顶，不出现负数），仅申请或已批准但未收货的退货仍按已售出计。粒度是成交件数，不是库存：有库存的商品可以出现在已售出列表，库存为 0 但从未成交的商品不会出现。
- 四个快捷入口统一为等宽四列、线性黑白图标（`Boxes` / `AlertTriangle` / `Sparkles` / `Receipt`）+ 标签 + 真实数量；数量未读取完成时显示 `—`，不显示 0 或占位假数字。进入商品页时读取一次已售出汇总，读取失败可点击入口重试并给出既有通知提示。
- 已售出列表的每一行显示该商品的累计净售出件数（`已售 N`），其他快捷筛选下不显示该数字。
- 规则单测：`tests/merchant-product-browse.test.ts`（搜索、低库存阈值、新款窗口、分区不重复计数、两层叠加、已售出归属）；`tests/merchant-product-sales.test.ts`（取消/草稿/整单退款排除、按 SKU 扣减退货、售出不等于售罄）。
- 所有计数在未过滤的商家商品集合上一次算出，切换任一层都不会重复累加；已售出汇总与商品集合按 `productId` 关联，不新增第二份商品数据。
- 固定区使用 `sticky top-0` + 不透明底色，列表内容在其下方滚动，不覆盖列表行。
- 默认进入“现货”分区；从首页“低库存商品”待办进入时，快捷筛选置为“低库存”并清除分区限制（分区行无选中项），保证列表数量与入口计数一致。
- 商品编辑锁（`/api/merchant/settings/product-editing`）只出现在商品详情“商品管理”卡片，仅 `canManageProductEditing` 用户可切换；列表页不放置该控件。
- 兼容：新增只读 `GET /api/merchant/products/sales-summary`；不新增数据库字段或权限，分区写入仍走 `visibility` / `status` / `isExclusiveProtected` / `protectionLevel`。

## 5. 逐页实施与验收方式

### 5.1 二级文案逐页清理

每个页面（含详情、弹窗、抽屉、筛选区、统计卡片及空/加载/错误状态）都须逐条检查，不得只查页面标题或用批量替换代替页面审阅。

**默认删除**：副标题、标语、功能介绍、卡片/字段/按钮旁的重复解释、装饰性描述、无意义空状态说明、统计值下方不影响理解的口径复述，以及可由字段名、状态或操作本身表达的文字。删除后不得留空白占位，也不得补写另一句介绍。

**必须保留**：法律/隐私告知、付款与费用规则、输入格式/必填/长度限制、权限和数据访问范围、不可逆/高风险操作提示、业务状态含义、影响用户决策的限制，以及准确说明失败原因、恢复方式或下一步操作的错误/结果信息。保留内容只改到足够短，不得删除其约束、后果或选择信息。单纯的营销、解释或开发状态文字不属于保留项。

**逐页检查清单**（逐条完成后才更新状态）：

- [ ] 主标题之外的副标题、标语、介绍和重复说明已逐项判断并清理。
- [ ] 指标、统计卡片及表格字段没有可删除的口径复述或装饰性标签。
- [ ] 按钮旁说明、卡片标题下描述、输入占位示例没有重复按钮/字段含义。
- [ ] 空状态只留真实状态和必要入口；加载、成功、错误提示仍准确且可操作。
- [ ] 权限、隐私、付款、安全、输入约束和风险提示逐项核对后保留或精简。
- [ ] 桌面、窄屏、移动 Web、小程序（适用时）的页面内状态、详情、弹窗和抽屉已纳入检查。
- [ ] 记录删改内容、保留理由、实际测试及视觉验收状态；未运行的页面不标记为已验收。

**搜索与验收标准**：

- 在 `src/apps/merchant-admin-web`、`src/apps/merchant-admin-mobile`、`src/apps/merchant-admin-common` 及 `merchant-miniprogram` 中分别搜索二级文案信号：`subtitle`、`description`、`helper`、`placeholder`、`所选时间范围`、`暂无`、`仅`、`请`、`帮助`、`说明`、`提示`，并审阅命中内容及调用页面。按 JSX/WXML 文本与 Tailwind 小字号辅助文案（如 `text-xs`、`text-[10px]`）回看页面上下文。
- 搜索仅用于建立待审阅候选，不得按关键词或字号机械删除；字段标签、真实状态、输入约束、权限/安全提示、错误/结果反馈、协议及隐私文案均按上述边界判定。
- 每页检查关联中英文资源和动态文案；确保没有被隐藏在详情、弹窗、折叠区或窄屏端的重复说明。字数检查只验证主标题/必要副标题的长度，不代替二级文案审阅。

### 5.2 页面实现与验证

每一页单独执行并在上表留记录：

1. 复核该页面路由/入口、角色和真实数据来源，检查现有改动与组件调用范围。
2. 先完成上面的二级文案清理清单，再记录布局、层级、留白、溢出、触控/键盘、空/加载/错误状态问题。
3. 仅做该页所需的 UI 修改，保留已有 API、权限、数据、操作及视觉体系。
4. 运行目标应用，在桌面/窄屏或小程序环境逐一检查页面与交互；检查失败则继续修改。
5. 运行与该页面相关的测试/构建，并记录命令、结果和截图/运行证据。
6. 只有文案清理、视觉与交互实际检查均通过才标“已优化且已检查”；环境无法运行则明确待验收。

### 5.3 商品发布页固定操作栏

> 2026-10-25：手机端全站形状令牌已统一为按钮/输入框 6px、卡片 8px、弹窗 10px、标签 4px；本文原 44px 按钮与 8px 圆角要求已同步收紧。详见 [`mobile-design-system.md`](../mobile-design-system.md)。

商品发布使用同一两步向导：第 1 步只处理媒体，第 2 步填写商品信息；桌面为居中浮层，商家手机 Web 为全屏浮层。底部操作栏在 320–767px 视口内单行显示，不得换行。

按钮高度 40px；手机操作栏左右内边距 12px、上下内边距 12px，栏高 65px，另加 `env(safe-area-inset-bottom)` 安全区。第 1 步从左到右为“取消｜下一步”，第 2 步为“上一步｜保存草稿｜发布商品”。第 2 步三个按钮按 1:1:2 分配可用宽度（`flex: 1 1 0%`、`flex: 1 1 0%`、`flex: 2 1 0%`），比例只作用于扣除栏内边距与两个 8px 按钮间距后的内容宽度：

- 390px 视口：可用按钮宽度 `390 - 24 - 16 = 350px`；上一步 87px，保存草稿 87px，发布商品 173px。
- 320px 视口：可用按钮宽度 `320 - 24 - 16 = 280px`；上一步 69px，保存草稿 69px，发布商品 138px。

取消、上一步、保存草稿使用白底灰边框；下一步与发布商品为黑底白字主按钮。按钮文字保持单行，不能裁切、遮挡或缩小到不可读；实测 320/390/430px 三个视口按钮 `scrollWidth` 等于 `clientWidth`，页面横向溢出为 0。布局不得覆盖按钮焦点状态或阻止键盘访问。第 2 步滚动区须能滚动到媒体区块完整可见，固定栏不遮挡末尾内容。


### 5.4 商家手机首页分步建设与 PWA 目标

**本阶段范围：** 以现有 `merchant-admin-mobile`（`MerchantMobileApp.tsx`）为唯一商家手机工作区，按用户提供的手机首页参考逐步整理首页。白底、黑色文字、浅灰分隔线；优先呈现品牌/页面标题、搜索、真实且可操作的常用入口、真实经营摘要、近期商品与待办。减少渐变大卡、冗长解释和空白区；手机底部导航、店铺身份、权限、现有业务 API 和导航状态保持不变。示例截图中的金额、商品、计数及增长百分比不得作为演示值写入，必须使用真实接口返回值；无数据时显示真实空状态。

**入口复用：** 逐个常用操作必须映射至现有商家商品、订单、库存、客户、POS/其他页面能力。现有工程未检索到独立手机报价/开单创建流程时，不新增假按钮或让入口误导至无关流程；补齐相应真实业务入口需单独按既有模块实现。

**渐进式建设：** 先验收首页导航和真实数据展示，再依用户后续优先级逐页整理商品、订单、库存等模块；每次只改当前明确范围并保持商家 Web、平台后台及小程序独立。最终再进行商家手机端 PWA 的安装、启动、更新、缓存、离线/网络错误策略和 iOS/Android 设备验收，不以单纯存在 manifest 作为 PWA 完成证明。

**现有 PWA 事实：** 仓库已有 `merchant-admin-mobile` 独立 Web 构建目标、`public/apps/merchant-admin-mobile/manifest.webmanifest` 和根级 `public/sw.js`。因此最终阶段优先核验及补齐现有安装/Service Worker 行为，不预先创建第二套应用、manifest 或 Service Worker。PWA 生产安装体验与离线行为当前未验收。
