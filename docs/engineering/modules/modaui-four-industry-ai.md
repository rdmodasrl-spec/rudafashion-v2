# ModaUI 四行业 AI 数据分析闭环规格

- 状态：部分完成（四行业只读分析已通过隔离 PostgreSQL/真实 HTTP 验证；三端登录态运行与完整行业目标仍待验收）
- 范围：百货批发、箱包批发、百货连锁、综合零售的商家 AI 只读分析工作流
- 不在范围：服装生产批发、服装批发、贸易批发的业务行为；新增 UI/导航；模型供应商接入；图片/视频付费生成；库存、采购、调拨、促销等直接写操作

## 1. 问题与目标

现有 ModaUI 已有统一商家任务入口、监督路由、工具运行时和四个核心 Agent，但这四个行业主要复用通用经营分析工具。行业提示词/模板并不能证明专业数据闭环。百货批发与百货连锁还共享粗粒度 `DEPARTMENT_STORE` 行业值，因此只按该值加载 Pack 会混淆两个不同模板。

本规格将四个目标行业的只读业务分析接入现有任务链，按服务端 `Merchant.industryTemplate` 区分行业工具。三端继续使用同一商家认证、任务 API、数据库和业务规则。目标是工具真实读取当前商家业务数据，并将可核对的结果写入现有 ModaUI 任务结果，不执行未经确认的业务变更。

## 2. 现状复用与防重复结论

复用现有实现，不新建聊天、身份、数据、API 或任务系统：

- 入口：Web/手机 Web 共用 `ModaUIWorkbench`；商家小程序 `pages/assistant`。
- API：`POST /api/merchant/modagpt/task/preview`、`POST /api/merchant/modagpt/task`、`GET /api/merchant/modagpt/task/:id`。
- 调度/执行：`modagptTaskSupervisor.ts`、`modagptMerchantTaskExecutor.ts`、`modagptRuntime.ts`。
- 行业权威配置：`Merchant.industryTemplate` 与 `merchantIndustryTemplates.ts`；旧 `Merchant.industry` 继续用于兼容和模块门禁。
- 商品属性：`Product.industryAttributes`、`ProductVariant`/条码；既有共享商品目录。
- 百货连锁：`MerchantStore`、`MerchantStoreStock`、`MerchantStoreTransfer`、`MerchantPosSale`。
- 综合零售：`MerchantPosSale`/`MerchantPosSaleItem`、商品与条码、既有 POS 销售写入流程。
- 箱包批发：现有商品材质、尺寸、容量、SKU 与商品目录字段。
- 员工/Agent 权限、租户校验、输入输出校验、审批、审计、超时与重试：继续由现有 `ModaGptToolRuntime` 执行。

新增的是四个模板专属的只读工具定义/handler 和相应 Pack/路由映射；不新增 Prisma 模型、迁移或 HTTP endpoint。百货批发与百货连锁必须以不同 `industryTemplate` 选工具，不能以共同的 `DEPARTMENT_STORE` 值作专业能力选择。

## 3. 四行业第一期闭环边界

| 模板 | 使用权威数据 | 只读工作流输出 | 不得推断/执行 |
|---|---|---|---|
| `department_wholesale` | 商品目录、变体/条码、`industryAttributes` 中现存包装/单位/批发字段 | 目录资料完整度、包装/单位字段缺失、可核对的商品/变体统计及最多 5 条商品级待完善字段 | 缺少换算关系时不得换算单位；不创建混批订单或采购单 |
| `bags_wholesale` | 商品目录、材质/尺寸属性、可选容量、SKU/条码 | 属性覆盖率、缺失资料、SKU 统计及最多 5 条商品级待完善字段 | 容量为可选统计字段；不声称视觉识别材质；不生成/改写商品图片，不自动修改目录 |
| `department_chain_retail` | 当前租户门店、门店库存、POS 销售及既有调拨记录 | 门店销售/库存分布、最多 5 条包含商品/SKU、来源/目标门店和数量的可解释调拨候选 | 不创建/确认调拨；建议不等于库存承诺；只使用当前商家门店 |
| `general_retail` | 当前租户 POS 销售明细、商品/条码目录、`InventoryBalance` 中按商品 SKU 汇总的现存/预留/在途量 | 销售表现、商品/条码资料缺失和按近期开单速度计算的补货候选 | 候选以近 `days` 销量线性外推 14 天覆盖，计算 `max(0, ceil(日均销量×14 - max(0,现存-预留+在途)))`；不使用币种金额推断需求，不使用 `Product.moq` 作为再订货点，不改库存、不建促销、不创建采购 |

首期闭环的“分析”必须来自数据库查询和可追溯计算，不以模型生成的文字替代数据。输出须列明统计窗口、样本数量、缺失字段和不可推断项。模型自然语言润色、图像识别/编辑及付费供应商调用不作为该闭环的必要前提，未验证时仍标记为待验证/未接通。

## 4. 身份、API、权限与租户边界

- 商家身份只从既有认证中间件获得；忽略/拒绝客户端提供的 `merchantId`、行业或模板。
- 任务预览、创建和轮询沿用现有端点和错误契约，不新增公开聊天工具入口。
- 服务端读取并验证 `Merchant.industryTemplate` 与 `Merchant.industry` 一致；缺失模板的旧商家只保留旧通用工作流，不猜测四行业身份。
- 工具仅在匹配的模板 Pack/路由中注册；员工权限仍须满足工具声明的 `business.analytics.read`（并接受现有 Agent 权限双检）。
- 每个 Prisma 查询都必须带当前认证 merchant ID；门店/商品/销售关系也须限定该商家。不得用客户端提供的对象 ID 作无租户约束查询。
- 工具为只读、幂等；不会写库存、采购、调拨、促销或订单，不需要审批令牌。未来增加写操作必须另立规格，走现有审批与业务服务。
- 综合零售补货建议必须按 `productId + sku` 匹配 POS 明细与库存余额，当前库存跨租户仓位按商家归属汇总；销售或库存查询达到安全行数上限时不输出补货数量，仅说明结果不完整。没有对应库存记录时标记为未覆盖，不把缺失当作零库存。
- 商品目录资料检查只在结果中展示最多 5 条商品级待完善项（标识、名称和缺失字段）；门店调拨候选只展示最多 5 条实际商品/SKU、来源/目标及建议量。结果来自当前商家记录，不自动修改商品或创建调拨。
- 数据访问失败、模板冲突、无权限和无数据均返回明确任务状态/错误；无数据与接口失败不得都伪装成空数组。

## 5. 三端流程与兼容

1. Web、手机 Web、小程序通过各自现有 ModaUI 入口提交同一任务预览/任务创建请求。
2. 服务端从认证商家读取模板，Supervisor 选出业务分析工作流及模板专属工具。
3. 运行时对身份、租户、员工和 Agent 权限进行校验，再调用只读 Prisma handler。
4. 结果经现有任务状态/轮询 API 返回并显示；三端不维护独立业务算法或数据源。
5. 已有公共文本聊天保持不变；未认证的公共聊天不能注册这些商家工具。

不修改工作台布局、颜色、导航、文案或交互，只扩展服务端工具与工作流数据。端侧页面视觉验收需真实运行；环境不可用时如实记为待验证。

## 6. 状态、失败、重复请求与恢复

- 查询没有记录：返回有结构的“无业务数据”结果，明确样本数为零。
- 权限拒绝、租户不匹配、模板缺失/冲突、数据库异常：走现有任务失败状态与错误码，不返回成功形状的空结果。
- 只读工具天然可安全重试；任务提交仍复用现有幂等键。重复提交不得造成业务副作用。
- 门店调拨只给建议；执行必须由用户通过已有调拨业务流程确认。
- 本次不需要数据迁移。代码回滚后，既有通用业务分析与旧任务 API 保持可用。

## 7. 验收标准

- 模板映射测试证明百货批发与百货连锁分别注册正确工具，且互不调用。
- 每个工具具有定义、输入/输出校验、真实 handler、Agent/员工权限声明及可执行测试。
- 综合零售补货候选使用真实 POS SKU 销量和真实库存余额；库存缺失、在途/预留量和结果截断边界须有测试证据；不产生库存/采购写入。
- 百货批发与箱包批发需输出有真实商品依据的待完善字段清单；百货连锁需将真实调拨候选显示在任务摘要中，且不写入调拨表。
- 隔离 PostgreSQL + 真实 HTTP 测试覆盖有数据、无数据、员工权限拒绝、跨商家 ID、错误模板、重复任务及数据库异常。
- 至少验证同一服务端 API 契约可供 Web、手机 Web、小程序调用；没有真实登录态运行截图的端不得标为实机已验收。
- 保护服装生产批发、服装批发、贸易批发既有工具与行为；无 schema migration、无外部模型调用、无生产部署。
- 最终报告区分代码、自动化、端侧实机和生产发布状态。
